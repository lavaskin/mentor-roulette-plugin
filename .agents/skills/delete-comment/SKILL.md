# Delete comments

The repo has no code comments: code says what it does, and a decision behind it lives in an ADR (`docs/adr/`, [0001](../../../docs/adr/0001-no-code-comments.md) is the rule). CI's Check comments step holds the line: `check-comments`, an action in `lavaskin/ffxiv-workflows` that the API shares. It's a ratchet against the `baseline` in `.github/check-comments.json`, which lists how many comments each file may still have. The baseline is empty, so any comment fails it.

## Running the check

With `ffxiv-workflows` cloned beside this repo, from the repo's root:

```sh
dotnet run --file ../ffxiv-workflows/check-comments/check-comments.cs -- check
```

`-- list [path prefix]` prints every comment counted as `file:line: preview`, and `-- update` lowers the baseline. `--file` matters: without it, `dotnet run` in a folder with a project runs that project.

## When the check fails

- **"over its N":** a change added comments. Delete them, sorting each as below: a decision goes to an ADR and an excuse gets a ticket. Never raise the baseline: `update` only ever lowers it.
- **"under its baseline":** comments were deleted from a file the baseline still lists. Run the check with `update` and commit `.github/check-comments.json` with the change.
- **A file was moved or renamed:** its baseline entry doesn't follow it, so the new path counts as a new file. Empty it of comments as part of the move.

## What the check counts, and what's allowed

It reads every file git knows (tracked or new, not ignored): comment trivia in C# (`//`, `/* */` and `///` doc comments, read through Roslyn, so `//` in a string isn't one), `<!-- -->` in `.csproj` and `.props`, `#` in the workflows and `.github/scripts/`, and `//` in `.vscode/*.json`. Comments on consecutive lines count as one.

Not counted, and left alone: tool directives (`// <auto-generated />`, `// ReSharper disable`, `// language=`, `# shellcheck`, shebangs). The full list is `Allowed` in `ffxiv-workflows`' `check-comments/check-comments.cs`. `#pragma`, `#nullable` and `#if` aren't comments.

## The pass

1. **Pick the scope** with `list`, and a path prefix to narrow it (`list MentorRouletteTracker.Core/Recording/`).
2. **Sort every comment,** reading each file in full first, since a comment's category depends on the code around it:

   | Category | Meaning | Action |
   |---|---|---|
   | Tautology | Repeats what the code shows (names, types, obvious flow), or is a section label | Delete |
   | Stale | Names code, files or behaviour that's no longer true. Grep for what it names before deciding | Delete |
   | Excuse | Explains away a hack: a workaround, "for now", "remove once", a known limitation, a hard-coded value or duplication, a timing hack, a `!` or cast hiding a type mismatch | Delete, and file a ticket to fix the hack |
   | Decision record | Why the code is this way when the obvious alternative would be wrong: how Dalamud or the game behaves, a threading rule, the contract with the site's API, a privacy reason, units or time zones, an ordering, what null means, reading files saved by older versions. Deleting the oddity without knowing it would cause a bug | Move into an ADR, then delete |

   - When unsure between tautology and decision record, it's a decision record.
   - A property comment with a fact the code can't show (units, what `null` means, where a value comes from) is a decision record. One that restates the name is a tautology.
   - A decision `AGENTS.md`, `README.md` or `docs/` already states needs nothing more. What a player sees belongs in `docs/runs.md`, and building and trying a build in `docs/development.md`, rather than in an ADR.
   - **A comment saying which real bug a test guards against** goes into the test's name instead, ending `_Regression_<WhatWentWrong>` (`Wipes_AreCountedOnce_Regression_TheGamesMessageCountedASecondWipe`).
3. **Delete only comments.** No renames, reformatting or code changes, apart from the test names above. Don't leave two blank lines in a row, or a blank line just inside `{ }`, where a comment was. For a big pass, split the files into batches by folder and give each to a subagent with these rules, telling them to edit only their own files, not to touch git and not to build or run tests (they share `bin/` and `obj/`). Have each write its excuses and decisions to a report for you to collect.
4. **Decision records into ADRs** (`docs/adr/`, the format is in `docs/adr/README.md`). Add to the ADR that already covers the topic, or start a new numbered one. Write each decision so it stands alone without the code beside it, with every fact the comment had, naming the files and symbols it's about. The repo is public: an ADR names no one, and says what the code does and why, not its history.
5. **Excuses into tickets** in `lavaskin/ffxiv-hub`, following its `CONTRIBUTING.md`: type Task, labels `plugin` and `tech debt`. Small ones are bundled into one "Tech debt: …" ticket, and anything around 2 points or more gets its own. Each item says where the hack is, what it does, and what a proper fix involves.
6. **Check:** the comment check passes, and `dotnet build -c Release` and `dotnet test` pass.
